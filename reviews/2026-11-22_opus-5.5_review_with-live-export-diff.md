## 0. Verdict in one paragraph

The Telethon plumbing works. The QR login flow is decent. The code is readable and
there are 87 passing tests. **But the core of the thing, the "smart cache", is
broken by design. It silently loses messages, serves stale edits forever, and
duplicates messages at the seams.** The export format also throws away things you
said are critical. Formatting with link URLs, reactions and service events are
gone. Polls become empty messages. Pin events become fake empty "replies".

On top of that, "authentication" is a string anyone can guess. With `CORS *`, any
web page you open in a browser can read your whole Telegram through
`localhost:8000`.

It is not shit everywhere, but the part you care most about, *"does the export
lose important details"*, gets the answer: **yes, it does, and sometimes it loses
whole messages without telling you.**

## 1. What is this actually trying to do?

Strip off the README marketing ("🚀 smart caching", "atomic commits") and the
real goal is:

> Give an AI agent (see `TELEGRAM_SCRAPER_SKILL.md`) an HTTP way to read *my*
> Telegram history. Keep a local copy so that repeated reads are fast and media
> is on disk.

That is a fine goal. The problem is that the code tries to be two things at once:

- a **transparent read-through cache** (`GET /history` decides by itself what to
  fetch), and
- an **archive** (`POST /sync`, the SQLite DB, media on disk).

A read-through cache needs a correct coverage model. An archive needs fidelity
and refresh. Right now you have neither.

---

## 2. Does it achieve the goal?

### 2.1 The cache coverage model is wrong (critical, silent data loss) [REPRODUCED]

`operations.get_cached_date_range()` returns **`(min(date), max(date))` of all
cached messages**. Then `find_gaps()` treats everything between these two values
as cached.

So:

```
sync 2024-01 … 2024-02
sync 2025-01 … 2025-02
GET /history 2024-01 … 2025-02
```

→ "cached range" = 2024-01 … 2025-02 → **zero Telegram requests** → the whole of
2024-02 … 2024-12 is simply **not there**, and nothing in the stream says so.

The mock run had 39 messages on the "server", and history returned **8**.

This is the worst bug in the project. One request with a narrow date range
followed by another narrow range at a different time poisons the cache **forever**
for everything in between. The only way out is `force_refresh=true`, and nobody
knows when to use it.

### 2.2 Cached messages are never refreshed: edits are lost [REPRODUCED]

When a range is "cached", it is served from SQLite and never compared with
Telegram again. If a message is edited after you cached it, history keeps
returning the old text and the old `edit_date`. You told me that "was it edited"
is critical, and the tool will happily tell you "no" for any edit made after the
first sync.

The same is true for deletions: deleted messages stay in the cache. For an
archive that is arguably a *feature*, but it is not marked anywhere either.

### 2.3 Duplicates at every seam [REPRODUCED]

Gap segments and cache segments are both inclusive on both ends
(`message.date > end_date` → break; SQL `date >= start AND date <= end`). The
message that sits exactly on `cached_start` / `cached_end` is emitted **twice**:
once from Telegram and once from the cache.

Mock run: ids `[1, 2, 2, 3, 4, 5, 5]`.

The default `end_date=now` always creates a gap that starts at `cached_end`, so
**almost every normal history call duplicates the last cached message.**

### 2.4 A truncated stream looks exactly like a complete stream

`GET /history` returns `StreamingResponse`. Once the first byte is sent, the
`try/except` around it is useless. A `FloodWaitError` longer than 120 s, a network
drop or a DB error in the middle of the stream just closes the connection. There
is no `event: error`, no `event: done`, and no total count. The consumer (your
agent) **cannot tell "the chat ends here" from "the server died here".** For an
export tool this is a data-integrity bug, not cosmetics.

### 2.5 The "atomic batch" is not atomic

`download_from_telegram_batched` says "save batch atomically", but
`store_media_with_uuid()` calls `session.commit()` **inside the loop**. Each media
row commits the half-written batch. Also, `stream_messages_with_cache` does
`client.get_messages()` + `download_media()` for *each* cached message with
missing media (repair), with the DB session open. That is a slow path disguised
as a cache read.

### 2.6 Pagination by `ORDER BY date … OFFSET`

`date` has one-second resolution and is not unique. OFFSET pagination over a
non-unique sort key has no guaranteed stable order for ties. Albums (several
messages in one second) are exactly that case. Use `ORDER BY message_id` (it is
monotonic per chat) and keyset pagination (`WHERE message_id > last`).

service events and polls are lost or corrupted. In your DM chat, about **30% of
messages have reactions** and none of them survive.

### 3.3 The real fix: store the raw message, derive the flat view

You keep adding columns one by one (`reply_quote_text`, `fwd_*`, …), and each one
needs schema + insert + update + 3 serializers + docs. That does not scale, and
you will always be one Telegram feature behind.

Do what every serious archiver does:

- Add a `raw` column (JSON) to `messages` with `message.to_dict()` (with a
  serializer for `bytes`/`datetime`). **Never lose anything again.**
- Keep a small flat set of columns for querying (`id, date, edit_date, sender_id,
  reply_to, is_service, text`).
- Build the API response from `raw` with **one** function. Add `text_entities`
  (or `message.text` as markdown) and `reactions`. For service messages, add
  `action: "pin_message"`.
- When you need a new field later, you only change the serializer, and it works
  for already cached data without a re-download.

## 4. Every stupid / half-assed part, by name

- **`get_cached_date_range` + `find_gaps` + `find_covered_range` +
  `build_timeline` + `merge_overlapping_ranges`.** About 120 lines of interval
  logic built on a wrong model (one min/max range). `merge_overlapping_ranges` is
  not even called anywhere. Delete all of it (see §5).
- **Three different message serializers.** One is the Telegram path in
  `stream_messages_with_cache` (hand-written dict), one is the cache path
  (`iter_messages_in_range` dict + `transform_message_to_response`), and one is
  `search._message_to_result`. They already disagree:
  - search uses `msg.forward.chat_id` (marked id) and history uses the bare
    `channel_id`;
  - `MessageResponse` (the OpenAPI model) lacks `forwarded_from_user_id/name/date`
    that the stream really sends.

  `transform_message_to_response` pops keys and the comment says "Transform to
  nested response format", while it is flat.
- **`download_from_telegram_batched`.** It is a 250-line function. The forward
  resolution block is duplicated for user and channel, and the "save batch" block
  is copy-pasted for the full and the final batch. Also, the
  `except Exception: raise` around each message makes one weird message (for
  example an unknown media type that throws) kill the whole export.
- **`batch_upsert_messages`.** It uses `getattr(msg, "...")` 20 times on a
  dataclass you own, and the insert and update branches duplicate every field. It
  does one `SELECT` per message plus one `session.get(User)` per message: N+1
  queries. Use `INSERT … ON CONFLICT DO UPDATE` with one statement per batch.
- **`upsert_user` overwrites names with `None`.** A forwarded-user row with
  missing data wipes good data from an earlier message.
- **`sender_id=message.sender_id or 0`.** Anonymous admins and some service
  messages become user `0`, and a fake user row `0` is upserted.
- **`find_media_by_uuid`.** It opens **every** dialog DB on disk to find one UUID.
  With 200 chats that is 200 SQLite opens per file request. It also swallows all
  exceptions.
- **Engine per call.** `get_session()` creates a new SQLAlchemy engine each time
  (and registers a new event listener). Engines are meant to be cached.
- **`history.py`.** The comment says
  `# FIXME: Ugly vibe-coded approach … datetime(2013, 1, 1)`. Yes, it is. Use
  `offset_id=0` / `min_id` and no dates at all.
- **`get_history` vs `sync_dialog_endpoint`.** Same 40 lines (parse dates, ensure
  dirs, create engine, upsert dialog) copy-pasted. Also, `sync` returns 200 with
  zeros for `start >= end` while `history` returns 400.
- **`sync` is a blocking POST** that can run for an hour with no progress and no
  cancellation. The HTTP client will time out first.
- **`download_media`.** It uses `glob(f"{message.id}-*")` on the media folder for
  every message (a directory scan per message). It also contains a FloodWait sleep
  on top of Telethon's own `flood_sleep_threshold=120`.
- **Dialog ID format is inconsistent.** `/search/dialogs` returns the bare
  `entity.id`, `/search/messages` returns the marked `chat_id` (`-100…`), and the
  cache directory is named by whatever string the client passed. The same chat can
  end up in two cache directories. Bare positive ids are also ambiguous between a
  user and a channel. Pick marked ids (`utils.get_peer_id`) everywhere.
- **README drift.** It says `0.0.0.0` (the code says `127.0.0.1`), `channels/`
  (the code uses `dialogs/`), `/api/v1/` in docstrings (the code uses `/api/v3`),
  and "atomic commits". Also, `version="1.0.0"` in FastAPI while the package
  version is `0.2.0`.
- **Dead code.** `check_db_connection`, `get_media_uuid_by_message_id`,
  `merge_overlapping_ranges`, `_qr_sessions` declared twice "to fix a forward
  reference", and commented-out code in `load_settings`.

## 5. Architecture: client-server, auth, caching

### 5.1 Is client-server wrong in principle?

**No.** For your use case (an AI agent reading your Telegram), a long-running
local server is the right shape:

- a Telethon session file can be used by only one process at a time;
- keeping one connected client avoids reconnect cost and flood limits;
- an agent can speak HTTP/JSON easily, and you can later expose it as an MCP
  server with almost no change.

What *is* wrong is **what the server pretends to be.** It pretends to be a
transparent cache over Telegram, and that is a really hard problem: coverage
intervals, edits, deletes, consistency. You do not need to solve it. Split it into
two dumb, obvious operations:

1. **`sync(dialog)`**: an incremental, **id-based** sync.
   - New messages: `iter_messages(entity, min_id=max_cached_id, reverse=True)`.
     Message ids are monotonic per chat, so "what is new" is one integer. You need
     no date-range bookkeeping.
   - Backfill old history: `iter_messages(entity, offset_id=min_cached_id)` until
     the start. Store a `fully_backfilled` flag per dialog.
   - Edits: re-scan the last N days (configurable, for example 30) on each sync
     and upsert. Edits happen mostly to recent messages. This is cheap: 100
     messages per request. Offer `full_rescan=true` for paranoia.
   - Store `last_synced_at` per dialog and return it in every response.
2. **`read(dialog, from, to)`**: **only** from SQLite, ordered by `message_id`,
   with keyset pagination, and with a final `{"done": true, "count": N,
   "last_synced_at": …}` event.

`/history` can still call `sync` first if you want "always fresh" behaviour. Then
the code is still trivial: the cache is *the archive*, not a guessing machine.

This removes `find_gaps`, `build_timeline`, the segment loop, the duplicate
seams, the hole bug and the stale-edit bug, all in one go.

### 5.2 User verification by username: you are right not to like it

`X-Telegram-Username` is **not authentication, it is a selector.** Concretely:

- **Any web page can read your Telegram [REPRODUCED].** CORS is
  `allow_origins=["*"]` + `allow_credentials=True`. A preflight from
  `Origin: https://evil.example` asking for `x-telegram-username` gets `200`, and
  the origin is echoed back. So any page you open in your browser can `fetch`
  `http://localhost:8000/api/v3/history/...` with your username (it is your public
  Telegram handle, or easy to guess) and read the response. Binding to
  127.0.0.1 does **not** protect against this.
- **`POST /auth/qr` with `force: true` is unauthenticated.** Anyone who can reach
  the port can **delete your session file** (`session_file.unlink`). The Telegram
  authorization itself stays alive as an orphan in "Devices".
- **The username goes straight into a filesystem path.** The header
  `../sessions/alice` passes the auth check [REPRODUCED]. In `/auth/qr` the same
  string is used to create and unlink `*.session` files. Validate it with
  `^[A-Za-z0-9_-]{1,64}$`.
- **"Multi-user" is fake anyway.** The cache is `dialogs/<dialog_id>/`, which is
  **not partitioned by account**:
  - user B can read user A's cached chats;
  - `/files/{uuid}` serves anyone's media to anyone;
  - two accounts that both have a private chat with the same person write
    **different message-id spaces into the same DB** (private-chat message ids
    are per account). This corrupts both.
  - `PATCH /settings` is global, so any "user" changes them for all.

**Recommendation (simple):**

- **One server = one Telegram account.** Drop the username header completely.
  The account is chosen at startup (`--session odetilie`). This matches how you
  really use it, and it removes the whole class of cross-user bugs.
- **Auth with a random bearer token.** Generate it on first start, store it in
  `data/token` (0600), and require `Authorization: Bearer …` on every route,
  including `/auth/qr`. Jupyter does exactly this. For an agent on the same
  machine, it just reads the file.
- **Remove `CORSMiddleware`**, or set it to an explicit allow-list. You have no
  browser front-end.
- If you ever *really* need multiple accounts, partition everything:
  `data/<account>/dialogs/...`.

### 5.3 Concurrency

- **`get_telegram_client` yields while holding the per-user lock [REPRODUCED].**
  On FastAPI 0.128, dependency teardown runs after the response is sent. So
  **one long SSE history or `/sync` blocks every other request** of the same
  user (search, dialogs, another history) until it finishes. The lock only needs
  to cover the *creation* of the client. Telethon is fine with concurrent
  requests on one client.
- All SQLite calls are synchronous inside `async def` routes, so they block the
  event loop. For a single user this is acceptable; just know it.

## 6. Where to simplify until it is almost trivial

Target shape, in rough line counts:

```
telegram.py   ~150  connect, iter new/old/recent messages (by id), download media
store.py      ~150  sqlite3 (or SQLModel) with raw JSON + few columns, upsert ON CONFLICT
serialize.py  ~120  ONE function: raw Telethon dict -> API dict (entities, reactions, service action, media meta)
api.py        ~250  /dialogs, /folders, /sync, /history (read-only from DB + done event), /files, /search, /auth/qr
```

Concretely:

1. Delete the date-interval machinery. Use id-based sync (§5.1).
2. Store `raw`. Use one serializer (§3.3).
3. Use one DB per account (or per dialog, fine), with **one cached engine per
   file**.
4. Store `dialog_id` + `message_id` in `media_files`, so `/files/{dialog}/{msg}`
   can be addressed directly. Drop the UUID indirection and the "scan all DBs"
   loop.
5. History stream: `ORDER BY message_id`, keyset pagination, a final `done` event
   and an `error` event.
6. `sync` as a background job: `POST` returns a job id, `GET /sync/{job}` shows
   progress. Or SSE progress. Not a one-hour blocking POST.
7. Use the dialog id in the marked form everywhere.

## 7. What is missing that a competent developer would notice immediately

- **A fidelity test against a real export.** You have perfect ground truth
  (`result.json`) and no test uses it. Write a script that, for a synced dialog,
  joins on `id` and reports per field: missing ids both ways, `edited`
  mismatches, `reply_to_message_id` mismatches, forward mismatches, and
  entities/reactions presence. Run it on these five chats after you re-auth. That
  is your regression gate.
- **A completeness signal in the stream** (§2.4).
- **Service messages as a first-class `type`** (`message` vs `service` + `action`).
- **Tests use only `FakeMessage`.** No test covers `MessageService`, polls,
  entities, reactions, or any real `telethon.tl.types` object. That is why none of
  the §3 losses were caught. Build test messages from real TL constructors (as I
  did with `MessageService(...)` in 3 lines).
- **Schema migrations.** `create_all` never alters tables. The next column you add
  breaks every existing DB silently (or loudly). With a `raw` column you mostly
  avoid needing migrations; otherwise add `PRAGMA user_version` and a migration
  list.
- **Timezone contract.** Dates are naive UTC strings without a marker; native
  exports use local time + unix time. Return ISO 8601 with `Z` or unix seconds.

## 8. What is good (yes, there is some)

- **QR login flow**: the background re-creation of the token every 25 s, the 2FA
  future and the cleanup on shutdown are thought through. The sequence diagram in
  the README is actually useful.
- **Config split** (env for secrets, CLI for infra, YAML for runtime knobs) is
  clean and well documented.
- Media metadata is recorded even when the file is not downloaded, and repair can
  fill it later. That is the right idea.
- Forward resolution caches entity lookups per run, which is good for flood limits.
- Reply quote text and offset are captured, which many tools skip.
- 87 tests run in 5 s with an honest mock. The *infrastructure* for good tests is
  there. The tests just don't test the hard parts.
- Defaulting to `127.0.0.1` (last commit) was the right move, but see §5.2 for
  why it is not enough.

problems:

- the min/max cache hole;
- the fake atomicity;
- auth by filename;
- the lock held across the stream;

That is a good sign the diagnosis is right. Below I list **only** the extra points
that I verified against the code myself.

### New points that I missed

1. **The Docker image is unreachable since `4cbade3`.** The server defaults to
   `--host 127.0.0.1` and the `Dockerfile` `CMD` is only
   `["--data-dir", "/app/data"]`, so `-p 8000:8000` reaches nothing. Fix:
   `CMD ["--host", "0.0.0.0", "--data-dir", "/app/data"]`. (Verified: both
   files.)
2. **`force_refresh` deletes the good media file before it re-downloads.** In
   `media_downloader.download_media` the existing files are `unlink`ed first. If
   the download then fails, you have no file at all. Download to a temp name and
   `os.replace` it. (Verified.)
3. **Search has inverted date semantics.** In `api/search.py` (lines ~220 and
   ~330), `start_date` is mapped to Telethon `offset_date` (the *upper* bound),
   and the error text is `"end_date must be before start_date"`. In `/history` it
   is the opposite. The same parameter names have opposite meanings in the same
   API, which is a trap for the agent. (Verified.)
4. **Search `total` is the page length, not the total number of matches.**
   (Verified: `total` is counted in the result loop.)
5. **`/files` and `/settings` check only that a session *file* exists.** They
   never check that Telegram still considers it authorized. Right now your
   `odetilie.session` is **revoked**, and it would still give access to every
   cached media file and to `PATCH /settings`. (Verified: both use
   `get_authenticated_user`, not `get_telegram_client`.)
6. **`PATCH /settings` returns success even when the YAML write fails**
   (`except Exception: logger.exception(...)`, then a 200). (Verified.)
7. **Dialog search sorts by `messages` before the counts are filled in.** Sorting
   by message count therefore sorts by `0`. `min_messages`/`max_messages` filter
   by the last message *id*, not the count. (Verified: the sort happens before the
   `message_count` assignment at line ~517.)
8. **Media is downloaded inline while the history stream is produced.** One big
   video stalls the SSE stream for the whole download. This is one more reason to
   move downloads into `sync`.
9. **The container runs as root** (there is no `USER` in the `Dockerfile`), while
   it holds the session files. (Verified.)
10. **`ruff check src/` reports 244 errors**, while the README presents it as the
    lint command. (Verified: 244, 180 auto-fixable.)
11. **If a message loses its media, it keeps the old `media_uuid`.**
    `store_media_with_uuid` runs only when the new message has media. This is
    minor, but it is the same "never reconcile" disease as §2.2.

### Where I disagree with the earlier reviews

- **Both reviews propose a `fetched_ranges` / `coverage` table**, which means
  tracking exactly which date intervals were fetched. That *fixes the hole*, but
  it keeps the date-interval machinery. It also does **nothing** for edits, which
  are your critical field. My §5.1 proposal is simpler and covers more:
  - **id-based** sync (`min_id` for new messages, `offset_id` for backfill);
  - a **rolling re-scan window for edits**;
  - **read-only** history.

  Message ids are monotonic per chat. "What do I have" is two integers plus a
  `fully_backfilled` flag, not a set of intervals. If you need arbitrary partial
  date windows without a full backfill, a coverage table is the right fallback,
  but store it as **id** ranges, not date ranges.
- **"One DB for everything."** I agree with one DB *per account*. Per-dialog DBs
  are not a disaster for a personal tool: you can delete or copy one chat easily.
  The real problems are the cross-DB UUID scan and the missing account partition.
  Both are fixed by putting `dialog_id` into the file URL and the account into the
  path. Do not spend a week migrating storage before §9 items 1–3 are done.
- **Neither review looked at export fidelity** (entities/URLs, reactions, service
  messages, polls). For your stated goal, this is the second most important
  finding after the cache hole. Store the raw message (§3.3).

### New finding: rich messages arrive as `MessageMediaUnsupported`

The two `rich_message` posts are long structured posts: headings, lists and
quotes. One is in SAVED INFO and one in Перестройка. Telethon 1.40 (layer 214)
receives them as `Message` with `MessageMediaUnsupported`, an empty `message`
and no entities. The scraper:

- classifies `MessageMediaUnsupported` as "no media";
- stores `""`;
- returns a normal-looking empty message.

**The whole content is gone, and there is no flag to say so.** Storing the raw
JSON (§3.3) would *not* save this one, because the data never reaches the client.
What you need:

1. **Flag it.** Add `unsupported: true` (or `media_type: "unsupported"`) so you
   know something is missing and can re-sync later.
2. **Watch for a Telethon release with a newer layer**, or switch to a client
   library that follows layers faster. Until then, this message type cannot be
   exported through this tool.

### Updated bottom line on export fidelity

- **Safe:** text, replies, edits, forwards, senders and media metadata on a
  first sync.
- **Lost:** reactions, link URLs, formatting, polls and service events. Service
  events are actively misleading.
- **Lost silently:** rich posts.
- **Unsafe over time:** anything served from the cache (§2.1–2.3).

The priorities in §9 stay the same, with one addition: **mark unsupported
messages explicitly.**
