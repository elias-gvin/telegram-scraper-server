# Linus-style review: the whole tree at `cb626d5`

*Reviewer: Claude Opus 5.5 (Fable 5.2 as advisor), 2026-11-22.*
*Scope: `main` is clean and there is no feature branch, so "the current branch change" means the
whole project at `cb626d5`. The last real change is `9da38fa`, the layer marker, so it gets extra
attention. I wrote this section before I opened any earlier review in `reviews/`.*

---

## Verdict first

**Is it good? The core, yes. Is it functional? Yes, for the normal path. Is all of it good? No.**

This repo is two projects glued together:

1. **A small, honest archive core** (`archive.py`, `sync.py`, `serialize.py`, `media.py`,
   `telegram.py`, about 1,270 lines). Somebody actually *thought* here. There is one contiguous id
   interval per dialog, it grows only from the edges, and each batch is written in one
   transaction. The raw `to_dict()` is the source of truth and there is exactly one serializer.
   Problems are recorded, never swallowed silently. The sync tests use real Telethon TL objects.
   I would merge this core, with the fixes below.
2. **Old legacy code that nobody rewrote** (`api/dialogs.py`, `api/auth.py`, `authenticate.py`,
   about 1,420 lines, roughly **39% of the source**). It has enum boilerplate, a copy-pasted date
   parser, its own FloodWait handling although a global handler exists, emoji `click.secho` spam,
   and `logger.error(..., exc_info=True)` everywhere. **All 21 lint errors in `src/` are in these
   three files.** `tests/mock_telegram.py` is a second fake, used only by `test_dialogs.py`.

What I actually verified:
- 156/156 tests pass (`uv run pytest`, 5 s).
- The real server starts in an empty scratch data dir. `/health` gives 200. No token gives 401.
  With the token, `/settings` works. With the token but no session you get a clean 401 that says
  "run tgsc-auth or POST /auth/qr". The token file is mode 600.
- I wrote throwaway probe tests against the project's own `FakeTelegram`. They **confirmed three
  real bugs** (described below). I deleted the probe tests afterwards.

What I did **not** verify: anything against live Telegram. I did not touch `./data` or your
real session. "Functional" here means *passes its own tests, starts, authenticates requests,
and the sync invariants hold on the fake.* It does not mean "I archived a 200k-message channel
and checked it".

`uv run ruff check src/` as the README says: **21 errors.** They come from the ruff 0.14 → 0.17
upgrade in `1f64aed` (the newer default rule set), and nobody saw them because **there is no CI**.
The README says that command is how you check the code, and the command fails. That is broken by
definition.

## 1. What is this actually trying to do?

Remove the marketing and the goal is:

> Keep a local, lossless, resumable copy of one Telegram account's chats, and serve it as JSON
> to an AI agent without hitting Telegram on every read.

The design really serves that goal. `messages.raw` is the full Telethon dict. Everything else is
derived and can be re-derived. That is the right call: when the serializer is wrong you fix the
serializer, not the data.

The latest commit (`9da38fa`, layer marker) tries to answer one question: "was this chat archived
by an older Telethon that could not see some content (rich posts), so do I need `full=true`?"
That is a real problem. The implementation is clumsy (see section 3).

## 2. Does it achieve the goal, or does it just move complexity around?

**Mostly it achieves it.** Interrupted syncs resume without holes (tested). Edits, reactions and
deletions inside `refresh_days` are picked up (tested). A broken message does not kill the stream
(tested). Account mixing is refused (tested). This is real engineering, not shuffling.

But the "nothing is silently lost" promise has holes that the README does not mention:

- **The deletion detector trusts dates to be monotonic in ids. They are not always.**
  `_refresh` (`sync.py:263-277`) walks newest → oldest and *stops at the first message older than
  the cutoff*. Then everything archived in `[cutoff, now]` that was not seen is marked
  `deleted`. One message with an old date and a high id (imported chat history keeps original
  dates) cuts the walk short. Every real, live message below it inside the window is then
  marked deleted.
  **Confirmed with a probe:** ids 1 (2 h ago), 2 (60 days ago), 3 (1 h ago). The second sync
  reports `deleted_messages=1` for message 1, *plus* a false
  `count_mismatch: Telegram has 3 messages, archive 2`. The raw message is kept, and
  `full=true` repairs it (also confirmed), so no data is lost. But the archive lies until
  someone runs a full sync. How often live Telegram produces this, I did not measure.
  **Fix:** define the refresh window by *id*, not by date. Take the lowest archived id with
  `date >= cutoff` from SQLite, then read `min_id=that-1` and compare id sets. No date
  comparison on the Telegram side at all.

- **`_check_count` is weaker than it looks.** `archived < total` only catches a *shortage*.
  Old deletions outside the refresh window stay `deleted=0`, so they inflate `archived`, and
  that can hide real gaps of the same size. The comment says "loud last check". It is a
  heuristic, so call it a heuristic.

- **A migrated basic group that cannot be resolved kills the whole sync.** `sync.py:139-151`
  recurses after the supergroup is already synced and committed. If `resolve(migrated_from)`
  raises, `POST /sync/{supergroup}` returns **404 "Dialog -X not found"** for a dialog that
  *did* sync. **Confirmed with a probe:** the supergroup row has `reached_start=1, layer=233`,
  and the caller gets `DialogNotFound`. That contradicts "problems never stop the sync". Catch
  it and put it in `report.problems` with `message_id=0`.

## 3. Stupid, over-engineered or half-done parts

**The layer marker (`9da38fa`). The latest change, and it is half-done.**
- `read_everything = state["high_id"] is None or (refresh and full)`. Interrupt the *first*
  sync, and the next sync sees `high_id` set, so `layer` stays NULL forever. **Confirmed with a
  probe:** 50 messages, failure after 25, resume. `report.layer is None`, and `stale_layer:
  archived with Telegram layer unknown` nags you to do a pointless `full=true` re-read of a chat
  that this exact client read completely. "Interrupted syncs are fine" is a headline promise of
  this project, and the newest feature breaks it.
- The whole "oldest layer of the dialog" idea is the wrong unit. Store `layer` **per message**
  (one INTEGER column, set in `save_message`). Then the stale check is
  `SELECT min(layer) FROM messages WHERE dialog_id=?`. `read_everything` goes away, the
  `coalesce` in `finish_sync` goes away, and the interruption bug goes away. Less code and
  correct. That is how you know it is the right design.

**`sync.py:92`: `GetFullChannelRequest` on every sync of every megagroup**, including every
`GET /history` call. `dialogs.migrated_from` is already stored. Telegram never un-migrates a
group, so read it from the archive and ask Telegram only once.

**`_download_media` loads every media row with its full `raw` JSON, on every sync**
(`archive.media_rows`, `fetchall()`). Downloaded rows skip the `json.loads`, but SQLite still
reads the blobs, and Python still holds all of them in memory. Then it does a `stat()` per file.
For a chat with 100k media messages that is hundreds of MB pulled in to download maybe three new
files. Select `raw` only for rows that are not `downloaded`, and do the disk check without
loading JSON. (From reading, I did not benchmark this.)

**`except Exception` swallows the wrong things** (`sync.py:243`, `sync.py:318`). A
`FloodWaitError` longer than `flood_sleep_threshold=120`, or a revoked session, raised during a
media download is recorded as `failed:FloodWaitError` on *that file*. Then the loop goes on to
the next file, hits the same flood, records it again, and so on for the whole chunk. Flood waits
and `SESSION_LOST` must propagate. (From reading.)

**`api/dialogs.py`, the worst file in the repo.**
- `msg_count = dialog.message.id` (`dialogs.py:421`) is used for `min_messages`/`max_messages`.
  The top message id is *not* a count. In private chats and basic groups, ids are per-account
  global counters, so a chat with 3 messages can have "count" 4,000,000. The filter is wrong
  for exactly the dialogs people filter.
- `sort=messages` sends one `getHistory` per dialog, sequentially, over *all* dialogs. With 800
  dialogs that is 800 requests for one HTTP call. That is a flood-wait generator with a REST
  API on top.
- `_parse_date` is a copy of `deps.parse_date`. `_entity_title` is a copy of
  `telegram.title_of`. It has its own `except FloodWaitError → 429` although `server.py` already
  maps `FloodWaitError → 429` globally. It uses `str, Enum` where the rest uses `StrEnum`. 618
  lines for "list dialogs, filter, sort, paginate". It should be about 150.

**`api/auth.py` (QR login over HTTP)**
- `force=true` (`auth.py:259-261`) **deletes the working session before the new login has
  succeeded.** If the QR is never scanned, you just logged yourself out with nothing to replace
  it. Log in into a temp session file and rename it over the old one on success.
- An expired or failed QR flow leaves its half-made `.session` file. The `finally` only
  disconnects. The next `POST /auth/qr` then answers **409 "already has a session"** for a
  session that never authorized. The user must know to pass `force=true`. (From reading.)
- Nothing stops two concurrent `POST /auth/qr`: two Telethon clients writing the same SQLite
  session file.
- Sessions that reach `success` but are never polled stay in `_qr_sessions` forever. It is a
  small leak, but it is module-global state that also leaks between test apps.
- `submit_2fa_password` polls `asyncio.sleep(0.1)` 30 times, waiting for its own background
  task. Make the future return the result.

**`authenticate.py`**: 366 lines for "connect, QR or phone, maybe 2FA". Every branch catches
`Exception`, logs it with `exc_info=True`, prints an emoji, and returns `False`. Then the caller
turns `False` into `ConnectionError`, then catches `ConnectionError`, prints again, and returns
`1`. Telethon's own `client.start()` does phone + code + 2FA in one call. QR can be about 30
lines on top of it.

**Small stuff that still matters**
- `end_date=2025-01-05` parses to *midnight*, so the "Inclusive" end date silently drops all of
  Jan 5. The tests pass only because they use `"2025-01-05 12:00:00"`. A date-only end must
  mean end of day.
- `load_or_create_token` writes the file with the default umask, then `chmod 600`. For a short
  moment the token is world-readable. Use `os.open(..., O_CREAT|O_EXCL, 0o600)`.
- `GET /history` with no `start_date` on a big chat syncs the *whole chat* before the first
  byte. There is no SSE keep-alive comment during the sync, so proxies and agent HTTP clients
  will time out. Send `: syncing\n\n` periodically, or stream progress events.
- `_locks` and `_dialogs_refreshed_at` are module-global and never shrink. They are harmless
  in size, but they are global state that should live on `app.state`.
- `media_skipped` counts *all* skipped files of the dialog on every sync, not new ones.
  The report field lies a little.
- The recursive migrated-group sync adds only `problems` to the report. `new_messages` etc.
  of the old group are dropped.

## 4. What is missing that a competent developer would see immediately

- **CI.** One GitHub Action with `uv sync && uv run pytest && uv run ruff check`. The lint is
  already red, and nobody knows.
- **A test where dates are not monotonic in ids.** The whole deletion logic depends on that
  assumption, and the fake makes every test data set monotonic.
- **A test that interrupts the first sync and then checks the layer.** The probe above is that
  test, about ten lines.
- **Any test for `force=true` with a scan that never happens**, or for an expired QR followed by
  a new start.

## 5. Where the design can become almost trivial

- **Layer per message**, as described above. It deletes the `read_everything` logic.
- **Refresh by id range, not by date.** The deletion check becomes pure set arithmetic on ids
  that SQLite already gives you, and there is no clock and no cutoff edge case. (The test
  `test_refresh_window_edge_does_not_invent_deletions` exists *because* the date approach is
  fragile.)
- **`migrated_from` from the archive** after the first lookup. One less round trip per call.
- **Dialogs endpoint:** fetch `iter_dialogs()` once, filter in one function, sort, slice.
  Drop `message_count` filtering, or label it honestly as "top message id". Drop
  `sort=messages`, or cap it.
- **Auth:** the CLI should use `client.start()` plus a QR option. The HTTP QR flow should use a
  temp session and an atomic rename, and keep only one flow active at a time.

## 6. Where the implementation can become cleaner, shorter, more obvious

- `archive.transaction()` returns `self.db`, so `with archive.transaction():` really means
  `with sqlite3.Connection:`. It works, but nesting is a trap: any helper that uses
  `with self.db:` inside it commits early. Today no helper inside `_save` does that, but
  `set_media` does and it is one refactor away from being called there. Use explicit
  `BEGIN`/`COMMIT` with a savepoint-aware context manager, or document the trap where
  `set_media` is defined.
- `media.download`: if Telethon ever returns a path different from `partial`, the `finally`
  cleans up the wrong file. Pass a directory-free temp name and rely only on the returned path.
- `serialize.check()` runs the full serializer once per message at sync time just to catch a
  crash. That is fine, but `_save` then does `json.loads(raw)` right after `dump_raw` built it
  from a dict. Keep the dict, and serialize once.
- Run `ruff --fix`. Replace `logger.error(..., exc_info=True)` with `logger.exception`. Delete
  the empty `# Module-level state` banner in `auth.py`. Remove the `warnings.filterwarnings` in
  `__init__.py`, or explain which Telethon version still emits that warning.
- `tests/mock_telegram.py` and `tests/fake_telegram.py`: two fakes is one too many. Move
  `test_dialogs.py` to the real-TL fake.

---

## Bottom line

The core is good work. It is small, it has an invariant you can say in one sentence, and the
tests check that invariant against real Telethon objects. That is better than most "scraper"
projects by a big margin.

It is **not** "nothing is silently lost" yet:
- the date-based refresh can mark live messages deleted;
- the count check can hide gaps;
- the newest feature (layer marker) breaks on the exact case the project brags about
  (interrupted sync);
- a migrated group that cannot be resolved turns a successful sync into a 404.

All four are small fixes. Two of them *remove* code.

Then there is the 39% of the tree that is the old project in a new coat: `dialogs.py`,
`auth.py`, `authenticate.py`. It is not dangerous, except `force=true` logging you out. But it
is bloated, it duplicates the core, it is where every lint error lives, and its
`min_messages` filter is simply wrong. Rewrite it with the same discipline as `sync.py`, or cut
it.

**Score: core 8/10, periphery 4/10, project as shipped about 6.5/10.** It is usable today for its
real job. Fix the refresh window and the layer marker before you trust "deleted" or
"stale_layer" for anything.

## Addendum: what I took from the earlier files in `reviews/` (written after the verdict above)

*Everything above this line is unchanged. I read the earlier files only after I wrote it. Most
of them review the **old** code (before `4cbade3`). I checked each point against HEAD (`cb626d5`)
and kept only those that are still true there.*

### Evidence that changes my confidence (not my verdict)

- **The rewrite was checked against live Telegram, by the author, on real chats**
  (`2026-11-22_export-fidelity_tool-vs-native.md`, last section). It archived 178,596 messages
  over five full histories. Every message serialized without error, there were no count
  mismatches, and the comparison with Telegram Desktop's native JSON export found 0 field
  mismatches. I did not re-run this. But it means "functional" is backed by more than my fake
  probes: the normal path works on real data. The same file is honest about the gaps: no large
  channels, no forums, no comments, no bots, few media kinds. The bugs I found are in exactly
  those untested corners (imported history, migrated groups, interrupted first syncs).
- **The legacy files were left alone on purpose.** The rewrite plan (section 9) says:
  *"The untouched legacy parts (QR login internals, dialog search, the auth CLI) still have
  style warnings."* So the 39% "old project in a new coat" is a known debt, not an accident.
  It is still debt.
- **The plan measured `raw` at about 2.5–3 KB per message.** That supports my estimate for
  `_download_media`: 100k media messages × 3 KB means about 300 MB pulled into memory on every
  sync, only to find the few new files.

### Points from earlier reviews that are still true at HEAD, and that I missed or underweighted

1. **Synchronous SQLite work runs in the event loop** (prior-2 §3.3). It is still true after the
   rewrite. All `Archive` calls are plain `sqlite3` inside `async def` handlers. Short reads do
   not matter. But `media_rows().fetchall()` with all raw blobs, `json.loads` plus `check()` for
   every message in `_save`, and `serialize_row` for every row of a big history stream all block
   the loop. While that happens, every other request waits, including `/health`. For one user
   and one agent this is tolerable. For "run a full sync while the agent reads history" it is
   not. Fix the `media_rows` query first (it is the big one), and consider
   `asyncio.to_thread` for the serialize loop.
2. **Fuzzy dialog search ignores `order`** (prior-2 §4.2). It is still true:
   `dialogs.py:497-501` sorts by `(-score, field)` and never looks at `order`. The parameter
   is accepted and silently ignored.
3. **Dialog search is a full-account scan on every call** (prior-2 §4.3). It is still true:
   `iter_dialogs()` runs for every request, plus one `getHistory` per result on the page (or
   per *dialog*, with `sort=messages`). This is the same point as my `dialogs.py` section. Two
   reviewers found it independently, so it is not a matter of taste.
4. **`min_messages`/`max_messages` filter by the last message id** (Opus review, "new points"
   #7). It is still true at `dialogs.py:421`. I found it on my own; it was flagged before the
   rewrite and survived it. Sorting by `messages` *was* fixed (the counts are now filled in
   before the sort).
5. **`/health` proves nothing** (prior-2 §4.9). It still returns a constant. It is fine as a
   liveness probe, but then call it that. A useful `/health` would say whether the archive
   opens and whether a session file exists, without calling Telegram.
6. **Errors return `TypeName: message` to the client** (prior-2 §4.8). It is still true
   (`server.py:105-108`), and now there is a test that requires it. For a local single-user
   tool whose client is an agent, I think this is the *right* choice, so I agree with the
   observation and disagree with "fix it". The same goes for the absolute `file_path` in
   `/files?metadata_only=true` (prior-2 §4.7): local tool, local path, not a leak.

### Earlier points that are fixed at HEAD (so do not trust those files for them)

The fixes are: the Docker host and the non-root user, the atomic media download (`.part` plus
`os.replace`), the inverted search dates, `PATCH /settings` that now returns 500 when the save
fails, the per-account archive with an account check, an unauthenticated QR API that is now
behind the token, a truncated stream that now has no `done` event, and real schema migrations
through `user_version`. The rewrite really did close almost everything the September reviews
listed for the core.

### Where I disagree with an earlier file

- The rewrite plan (section 8) calls the end-of-sync count check *"an extra loud check"*,
  justified by three chats where Telegram's total equalled the iterated count. That holds for
  a fresh archive. On an older archive, old deletions outside `refresh_days` are never marked,
  so they inflate the archived count and can cancel out real gaps of the same size. It is a
  useful smoke alarm, but it is not proof of completeness. The README's wording ("checked
  against Telegram's own count") promises more than it gives.
- The Opus review (old code) argued for an id-based design with *"a rolling re-scan window for
  edits"*. The rewrite built exactly that, but it built the window on **dates**. My confirmed
  false-deletion bug lives in that one choice. The id-based idea should go one step further:
  turn the date cutoff into an id once (from the archive), then do everything else by id.

### Net effect on the verdict

None on the score. One sharpening: **for the normal path (the chats the author actually has),
the project is functional, and the author verified it live (I did not re-run that).** The defects are in the edges: the date-based
refresh window, the layer marker after an interrupted first sync, a migrated group that cannot
be resolved, and the untouched legacy third of the code.

### Corrections to the text above (the score does not change)

1. **The cause of the lint errors.** The top section says the 21 errors come from the ruff
   0.14 → 0.17 upgrade. That is only half true. I checked: with ruff 0.14.10, the tree before
   the upgrade already had **5 errors** in `src/`, and the rewrite plan says the legacy files
   were left with warnings on purpose. So the lint was already red, the upgrade made it 21, and
   the README command has failed since the rewrite. "There is no CI" is still the real problem.
2. **QR auth: concurrent flows.** If a flow is pending, its `.session` file already exists, so a
   second `POST /auth/qr` without `force` gets 409. That is the same mechanism as the "expired
   flow → 409" point. So two concurrent flows can only happen with `force=true`, which deletes
   the file of the first flow while its client still holds the file open. The point stands,
   but only for `force=true`. (From reading, not run.)
3. **What triggers the false deletion.** My probe proves the logic breaks when a higher id has
   an older date. It does **not** prove that real Telegram produces that. Imported chat
   history is a *candidate* trigger, not a confirmed one. The author's live run (178,596
   messages, no count mismatch) shows that it is rare at best on real chats. The fix (an id
   window) is still the right design because it removes the assumption, but the severity is
   "latent", not "observed". The same applies to the addendum line above that calls imported
   history an "untested corner": read it as "a possible trigger nobody has tested".

## Addendum 2: the reasons behind the decisions (from the original "Advisor fable" session)

*Written 2026-11-23. I read the session that built this code. The advisor's own replies in that
transcript are encrypted, so I could only judge the main model's arguments and the user's
choices. Rule I used: a reason only changes my mind if it is correct for the code that exists
now, not just plausible.*

### Where the reasons change my mind (severity goes down)

1. **`sort=messages` in dialog search.** The session found the burst problem itself, and fixed it
   on purpose: the count requests now go one at a time (there is a test for it), and a long
   flood wait stops the loop. So "a flood-wait generator" in my section 3 overstates it. What is
   left is **slowness**: one `getHistory` per dialog, in sequence, on every call. That is a
   design smell, not a ban risk.
2. **`GetFullChannelRequest` on every sync.** This was a conscious choice ("one request per
   sync to detect an upgraded group"), and one cheap request is fine. I downgrade it to a nit.
   Caching it is still trivially correct, because a migration never reverses.
3. **Long `GET /history` without keep-alive.** The plan's reason for having no background jobs
   is: *"a resumable sync makes them unnecessary: if a long `/sync` call times out, calling it
   again continues where it stopped."* That is true. A client that times out and retries does
   converge, because each attempt keeps its batches. So this is a UX cost (the agent sees errors
   until the sync is done), not a correctness problem. A `: syncing` comment every few seconds is
   still the cheap fix.
4. **Errors that return `TypeName: message`.** This was done on purpose, so the agent knows what
   happened. I already agreed in the first addendum, and the reason confirms it.

### Where the reasons do NOT change my mind

1. **Layer marker per chat instead of per message.** The session argued: *"Per-message tracking
   answers a question you won't act on per message."* That mixes up two things: **where you
   store** the layer and **how you report** it. You can store it per message and still report
   one number per chat (`min(layer)`). The per-chat storage is what made the code need
   `read_everything = high_id is None or (refresh and full)`, and that proxy is exactly what
   breaks after an interrupted first sync (confirmed by the probe). It gets worse:
   - The session's *own first rule* was "the layer of its last **complete** read: a sync that
     reached the first message, or `full=true`". The code does not implement that rule; it
     implements "the dialog was empty when the sync started".
   - The session's own numbers make the false alarm expensive: a full re-read of the 165k-message
     DM is "about an hour". A wrong `stale_layer` costs exactly that.
   - The session also said *"'old layer' mostly means 'maybe stale', rarely 'actually wrong'"*.
     So this warning is weak by design, and a weak warning that also fires falsely is how people
     learn to ignore warnings.

   The reason was a good argument against `refetch_below_layer`. It was not a good argument
   against a one-column-per-message design, which is *less* code.
2. **The refresh window based on dates.** The session checked the Telegram docs carefully, and
   recorded that *message ids* define the order inside a chat. Then it built the deletion window
   on *dates*. The docs it read guarantee the order of ids, not of dates. So the design argued
   from ids and was implemented on dates; nobody checked that step. My view is unchanged: the
   fix is an id window, and the severity stays "latent" (see correction 3 above).
3. **Leaving `dialogs.py`, `auth.py` and `authenticate.py` untouched.** The plan's reason:
   *"the dialog search redesign (it works and is not about export correctness)"*. The second
   half is a fair reason to *scope a rewrite*. The first half is false: `min_messages` and
   `max_messages` filter by the top message id, so that filter does not work. Two reviews before
   the rewrite also flagged it. "Out of scope" was the right call for that branch. It does not
   make the code good, and it is still 39% of the source.
4. **No async SQLite.** The plan says: *"With one user, blocking for a few ms per batch is fine."*
   That is true for the batch writes and the history reads. It is not true for
   `media_rows().fetchall()`, which loads the whole dialog's raw JSON on every sync. That query
   did not exist when the sentence was written. My point stands for that one query, not for
   async SQLite in general.
5. **The count check.** It was added because a spike showed exact equality on three freshly
   synced chats. On a fresh archive that is a fair test. It says nothing about an archive that
   is months old, where deletions outside `refresh_days` are never marked. Unchanged.
6. **QR `force=true` and the migrated-group failure.** Nothing in the session discusses either
   case. The plan maps an earlier review item, "`force` delete", as done, but the working session
   file is still deleted before the new login succeeds (`auth.py:259-261`). Unchanged.

### Net effect

The score stays the same. Three of my points get smaller (dialog count requests, the extra
`GetFullChannel` request, history keep-alive). The three probe-confirmed bugs and the legacy
debt stay as written. The pattern in the original session is good: it found and fixed many of
its own problems when asked "what if X fails?". Where it went wrong, the cause was the same
every time: a correct general argument applied to a slightly different thing than the code
actually does (ids vs dates, reporting vs storage, "it works" vs one filter that does not).
